## 第一性原理

核心洞见：**Agent的可靠性上限不取决于模型智商，而取决于控制流设计。**

这条规律的第一性原理拆解：

- **"不要让LLM决定普通代码已经知道答案的事"** → 知设Gotchas系统的25条领域映射规则纯代码层0.67ms/次，就是这条原则的实践。映射层根本不需要模型参与。
- **"围绕失败设计五种结果：Pass/Retry/Reroute/Escalate/Stop"** → 直接映射到知设架构：检索结果置信度低→Retry（换扩展词再查）；跨领域冲突→Reroute（切换到对应领域专家）；高风险报价建议→Escalate（设计师人工审核）；预算/Token耗尽→Stop返回部分结果。
- **"验证必须独立于创造"** → 知设"行业对齐"壁垒的核心难题。Gotchas库的验证不能让生成答案的同一个Agent自己验证自己，必须有独立的验证节点用确定性规则（甲醛国标唯一E0级、面积计算规则等）做Gate。
- **"上下文沿边流动，而不是堆积到一个大窗口"** → 知设谈单分析Agent的关键设计：客户画像、谈单记录、设计师Schema各是独立节点，信息通过结构化Evidence传递，而非塞进一个超长Prompt。

## 总结

级别判断：**L3 —— 架构级方法论，直接可指导知设Agent系统的设计演进。**

这篇文章最大的价值不是介绍了什么新框架，而是把Agent工程化的核心矛盾讲透了：**Prompt解决的是"模型说什么"，Graph解决的是"系统怎么运转"**。对于知设来说，Gotchas检索系统的现有架构（P0-P6六层流水线）已经不自觉地在用Graph思维——领域映射是Nodes，BM25+TF-IDF双召回是并行Edges，Reranker是Gate，精排Top-N是Synthesis节点。

但文章也暴露了知设当前架构可以升级的地方：

- **缺少显式的Retry/Reroute/Stop机制**：目前检索失败后怎么处理？
- **缺少独立验证分支**：Gotchas库的KU条目是否需要独立的Challenge节点来验证准确性？
- **三预算管理**：Token预算、时间预算、风险预算在谈单Agent里还没显式设计

一句话：**Prompt Engineering让你的模型更聪明，Graph Engineering让你的系统更可靠。**知设已经从直觉上走到了Graph架构的门口，这篇文章是把它显式化、系统化的方法论参考。

## 原文关键事实索引（已核实）

- 核心论点：Agent 无法稳定完成复杂任务，问题不在模型能力，而在控制流（Control Flow）架构——"完全按照提示词执行，但它仍然失败"
- 核心转变：Prompt Engineering 问"模型下一步该说什么/做什么"；Graph Engineering 问"当前应存在哪些信息？谁处理它？什么能证明结果正确？失败后流向哪里？"
- 四抽象：State（任务真正记忆，不要拿聊天记录当State）、Nodes（一个边界明确的任务；"研究所有内容再写报告"不是节点，是塞进一条Prompt的隐藏工作流）、Edges（固定边/条件边）、Gates（测试、Schema验证器、权限检查、确定性规则、评估模型或人工批准——"没有Gate的Graph只是更快传播错误的方法"）
- 五种失败结果：Pass / Retry / Reroute / Escalate / Stop；验证器返回结构化决策（如 `{"decision":"retry","reason":"...","target":"..."}`）而非"看起来不错"；"返回证据，而不是感觉"
- 验证必须独立于创造：同一个Agent既创造又批准自己的内容，"会成为一个糟糕的怀疑者"；Anthropic观点：Agent错误不断累积，"一个薄弱假设成为下一步的'证据'"，须设最大迭代次数等停止条件
- 三种预算显性管理：时间预算（并行汇合点等最慢分支）、Token预算（传结构化证据不传聊天记录）、风险预算（"读取文档和发送付款不应共享同一权限策略"）；预算耗尽返回最佳部分结果并说明原因
- 引用框架：Anthropic《Building effective agents》《Code execution with MCP》《Demystifying evals for AI agents》、LangGraph、AutoGen GraphFlow
- 真实示例：研究任务拆为9节点——Scope（输出Schema）、并行Collect Evidence Workers、Normalize（纯代码去重/拒绝缺失字段/统一日期）、Challenge（验证器找相反证据）、Human Gate、Synthesize（写作者只接收已验证证据）
- 何时不建Graph：任务短、风险低、易检查时一个模型调用就够；"Graph有价值，是因为它暴露复杂性，而不是制造复杂性"；"框架可以替换，但你的Graph决策才是真正的产品"
- 上手路径：从重复执行的任务画流程图→合并无法独立评估的节点→删除代码可替代的模型调用→拆分需要不同上下文的任务→输出前加验证器→"在增加Retry前加入Stop Rule"
