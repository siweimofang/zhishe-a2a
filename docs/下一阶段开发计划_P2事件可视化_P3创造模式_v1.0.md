## 一、P2 事件日志可视化（可开工）

### 1.1 现状盘点（事实）

后端基础已全部就绪（v0.1 已上线并验证）：

| 端点 | 功能 | 状态 |
|---|---|---|
| GET /gotchas/admin/effects | 副作用事件日志（上限 2000 条，新的在前） | 已上线 |
| GET /gotchas/admin/status | 运行时状态（条数/栈/索引/卸载/钩子/服务） | 已上线 |
| POST /gotchas/admin/rollback | 回滚（effect_id/批次/全量） | 已上线 |
| POST /gotchas/admin/unload | UNLOADING 两阶段（r1/r2） | 已上线 |
| POST /gotchas/admin/reload | 重载知识库 | 已上线 |

缺口：以上能力只有裸接口，没有可视化界面；回滚演练此前靠手工 curl（已做过一次实战演练），不可复现、不可回归。

### 1.2 功能点清单（规格）

P2 交付两个物件：

**交付物 A：运维面板（static/gotchas_admin.html，单文件）**

| 编号 | 功能 | 说明 |
|---|---|---|
| A1 | 鉴权输入 | 业务密钥 + 管理密钥两个输入框，仅存页面内存变量；刷新页面需重输；页面文件本身不含任何密钥 |
| A2 | 运行时状态卡 | 总条数 / 副作用栈大小 / 索引是否待重建 / 卸载态 / 钩子数 / 服务依赖就绪情况，5 秒轮询 |
| A3 | 事件流时间线 | 事件列表（时间/类型/副作用名/批次/详情），类型彩色标签：施加绿、回滚橙、失败红、跳过灰；支持按类型/批次/关键词筛选 |
| A4 | 回滚操作区 | 回滚最新一条 / 按副作用 ID 回滚 / 按批次回滚 / 全量回滚（protected 保留），所有破坏性操作先弹确认 |
| A5 | 卸载操作区 | UNLOADING r1（停止受理）/ r2（带守卫回滚） |

**交付物 B：回滚演练脚本（scripts/gotchas_rollback_drill.py，单文件）**

| 编号 | 功能 | 说明 |
|---|---|---|
| B1 | 一键闭环演练 | 热新增测试规则（固定 ku_id + 时间戳后缀）→ 业务检索验证命中 → 回滚批次 → 检索验证消失 → 输出逐步骤 PASS/FAIL 报告 |
| B2 | 密钥安全 | 从项目 .env 读取，不进命令行、不回显；演练结束必清理（失败路径也回滚） |
| B3 | 可回归 | 任何一次部署/升级后可重复运行，作为 P1 能力回归探针 |

### 1.3 用户场景

- 场景一（运维巡检）：后台出现检索异常，管理员打开面板 → 看到事件流里有 FAILED/rolled_back 记录 → 定位到具体副作用 → 决定是否回滚或补规则。
- 场景二（热更新演练）：上线前跑一遍演练脚本 → 6 步全部 PASS → 确认热更新+回滚链路健康；任一步 FAIL → 报告明确指到断点。
- 场景三（误操作止损）：批量加载了错误规则 → 面板一键按批次回滚 → 检索立即恢复原状（汇流性保证）。

### 1.4 技术方案（plan）

- 面板：单文件 HTML + 原生 CSS/JS，无框架、无外部 CDN 依赖（内网/隧道环境离线可用）；同源访问 /gotchas/admin/* 无跨域问题；fetch 头携带 `Authorization: Bearer <业务密钥>` + `X-Admin-Key: <管理密钥>`（v0.1 已定的双头约定）。
- 轮询：5 秒 interval 拉 status + effects，页面不可见时暂停（visibilitychange 优化）。
- 风格：克制留白——浅米白底、墨色正文、单一强调色（深酒红），符合项目审美基调；全中文界面。
- 演练脚本：标准库 urllib 实现（不引第三方依赖），读 .env 解析 A2A_API_KEY/A2A_ADMIN_KEY；测试规则用 `GZ-DRILL-<时间戳>` 命名，演练用规则独立于业务库（不污染 615 问法回归基线）。

### 1.5 任务拆解（tasks，每项 ≤2 小时）

| 任务 | 内容 | 验收 |
|---|---|---|
| T1 | 面板骨架 + 鉴权区（A1）+ 状态卡（A2） | 输入双密钥后状态卡数据正确渲染 |
| T2 | 事件流时间线 + 筛选（A3） | 事件类型标签着色正确、筛选生效 |
| T3 | 回滚/卸载操作区 + 确认弹窗（A4/A5） | 面板内回滚与 curl 等效，protected 规则不被误杀 |
| T4 | 演练脚本（B1-B3） | 6 步闭环全 PASS，失败路径自动清理 |
| T5 | 联调验证 | 面板浏览器实测 + 演练脚本连跑 2 次（含 1 次故意失败注入） |

### 1.6 验收标准

1. 面板无密钥时提示鉴权失败，输入双密钥后 30 秒内数据可见；
2. 事件流能展示 applied/rolled_back/FAILED/跳过四类状态且筛选准确；
3. 面板回滚一条副作用后，状态卡栈大小减一，事件流出现 rolled_back 记录；
4. 演练脚本全流程 PASS 输出报告；故意注入失败时能定位断点并完成清理；
5. 演练过程不改变知识库最终状态（演练前后 status 总条数一致、615 回归不受影响）。

## 二、P3 创造模式（方案调研与推演）

### 2.1 调研结论（事实）

1. **前置文档缺失**：方案文档 P3 行标注"前置：情报-04 Harness-R1 路线图对齐"，但全仓库检索（docs/feeds/config/skills 全覆盖）只有该方案文档一处引用"情报-04"，不存在独立路线图文档。情报编号体系中可确认的只有情报-15（DSH 论文，L3 9.5 分，本方案 v0.1 的理论依据）。
2. **可用相关资料**（非直接前置，但相关）：
   - `docs/deepseek_v4flash_harness_analysis_20260804.md`（L3）：核心共识 = 模型实际能力 = 潜在能力 × Harness 释放效率；Gotchas 库 = 装修行业"失败环境"，Skill+Harness 路线获战略级验证。
   - `docs/zhishe_architecture_improvement_list_20260804.md`（L3 衍生）：改进项 A"独立验证体系"，原则"验证必须独立于创造"；已有 P0-P6 流水线是 Graph 雏形，缺显式失败路径、独立验证分支、预算管理。

### 2.2 技术推演（判断，待情报-04 对齐后定稿）

**P3 定义**（方案文档原文）：临时规则/临时钩子（进程内存、重启消失）——情报-15 终局形态，自演化 Agent 基础。

**推演一：运行时基础已具备约八成**。v0.1 的落地路径（RuleManager 只改缓存 + `set_data()` 内存直通 + `persist()` 显式才落盘）与"临时规则不落盘"天然同构。P3 需要的增量是语义标记，而非新机制：

```
临时规则 = 普通 add_rule + 批次标记（batch_id="temp:xxx"）
         + persist() 前过滤临时批次（固化命令才写盘）
临时钩子 = HookManager.register（本身已是可逆副作用，无需新代码）
```

**推演二：创造模式 = 闭环的最后一块拼图**。自演化闭环：

```
Agent 发现知识缺口 ──► 现场创建临时规则（内存，秒级生效）
        ──► 检索验证命中（独立验证，对齐改进清单 A）
        ──► 命中且合理 → 固化（persist 落盘 + 入库流程）
        ──► 未命中/误伤 → 回滚丢弃（零残留，汇流性保证）
```

这正是"验证独立于创造"的运行时形态：创造（临时规则）与验证（检索回归）解耦，坏规则永远不会污染持久库。

**推演三：P3 的真正难点不在引擎，在决策层**。引擎层面是标记与过滤；难点是"Agent 何时有权创建临时规则、验证标准是什么、固化门槛多高"——这是 Harness-R1 路线图（情报-04）要回答的问题，也是"蒸馏禁区"（总宪章第九节）的运行时边界：临时规则只能由 Agent 从检索失败/真实场景提炼，不能凭空生成入库。

### 2.3 前置依赖清单（解锁条件）

| 依赖 | 状态 | 解锁后动作 |
|---|---|---|
| 情报-04 Harness-R1 路线图 | 缺失（仓库内无文档） | 产出 P3 正式方案（spec） |
| P2 可观测性闭环 | 本计划 | 创造模式需要可视化审计支撑（临时规则的全生命周期留痕） |
| 改进清单 A 独立验证体系 | 部分（P0 回归已存在） | 临时规则验证标准对齐 615 问法回归 |

### 2.4 结论（判断）

P3 不建议在本阶段排期。理由：前置路线图缺失，硬推会变成"按猜设计"，违背总宪章"先规格后实现"；而 P2 的可观测性闭环恰好是 P3 的前置（临时规则需要全生命周期审计），先做 P2 不浪费。P3 的引擎层增量很小（推演一），一旦情报-04 到位，实现窗口约 2-3 天。
