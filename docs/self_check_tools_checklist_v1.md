## 一、Gotchas库自检工具（优先级排序）

### 工具1：检索回归测试（P0 - 最高优先）

**解决什么问题：** 每次修改KU文本/重建索引后，无法确认是否破坏了已有查询的召回质量。

**规格：**
- 维护一份 `gotchas/tests/golden_queries.json`，包含20-30组"黄金查询"
- 每组：`{query, expected_top1_ku_id, expected_in_top3: [ku_ids], notes}`
- 测试脚本加载索引→逐条搜索→断言Top-1命中+Top-3包含
- 通过率 < 90% 则报警

**黄金查询初始集（从已验证案例提取）：**

| 查询 | 期望Top-1 | 备注 |
|------|----------|------|
| 闭水试验多长时间 | GZ-SY-00011 或 00298 | 2026-08-02校准后验证 |
| 电视墙50管验收 | GZ-SY-00208 | 2026-08-02校准后验证 |
| 线掉下来了 | GZ-SY-00208 | P6领域映射验证 |
| 马桶堵了 | GZ-SY-00005附近 | P6领域映射验证 |
| 防水刷几遍 | GZ-SY-00011 | 核心高频查询 |
| 墙面开裂 | 待确认 | 需补充 |
| 吊顶变形 | 待确认 | 需补充 |
| 地板起鼓 | 待确认 | 需补充 |
| 插座不够用 | 待确认 | 需补充 |
| 漏水到楼下 | GZ-SY-00011/00298 | 语义gap测试 |

**执行方式：** `python -m gotchas.tests.test_retrieval`
**触发时机：** 每次修改all_ku.json或重建索引后必须跑
**通过标准：** Top-1命中率 ≥ 90%，Top-3命中率 ≥ 95%

---

### 工具2：KU Schema合规校验（P0）

**解决什么问题：** 532条KU中可能有字段缺失、枚举值错误、长度超限等结构问题。

**规格：**
- 用 `gotchas/schema/ku_schema_v1.json`（JSON Schema draft-07）校验每条KU
- 检查项：必填字段存在、枚举值合法、title≤80字、description 50-500字、ku_id格式
- 输出不合规条目清单 + 具体违规字段

**执行方式：** `python -m gotchas.tests.test_schema_compliance`
**触发时机：** 每次批量修改KU后
**通过标准：** 0条违规（严格模式）或仅DRAFT级别允许轻微违规（宽松模式）

---

### 工具3：交叉引用完整性（P1）

**解决什么问题：** `related_ku_ids` 可能指向不存在的KU ID（删除/重编号后遗留）。

**规格：**
- 遍历所有KU的related_ku_ids，检查目标ID是否存在于all_ku.json
- 检查双向性：A引用B，B是否也引用A（警告级，非阻断）
- 输出悬空引用清单

**执行方式：** `python -m gotchas.tests.test_relations`
**通过标准：** 0条悬空引用

---

### 工具4：分片同步校验（P1）

**解决什么问题：** by_severity/by_stage分片文件可能与all_ku.json不一致。

**规格：**
- 重新从all_ku.json生成分片 → 与磁盘上现有文件做diff
- 任何差异 = 分片过期，需重新生成

**执行方式：** `python -m gotchas.tests.test_split_sync`
**通过标准：** diff为空

---

### 工具5：实战标准校准审计（P2 - 需人工参与）

**解决什么问题：** 库中可能存在"教科书标准 ≠ 行业实际执行"的条目（如闭水48h→24h）。

**规格：**
- 自动筛选高风险条目：evidence.source_type = "industry_standard" 且 frequency = "高频"
- 输出待审清单，由小马哥逐条判断"实际执行是否与描述一致"
- 校准后更新metadata.last_reviewed_at + version

**执行方式：** `python -m gotchas.tests.audit_calibration` → 输出待审清单 → 人工校准
**触发时机：** 每月一次，或累计新增/修改50条后
**通过标准：** 待审清单清零

---

### 工具6：索引新鲜度检查（P2）

**解决什么问题：** hybrid_index.pkl可能过期（all_ku.json修改后忘记重建索引）。

**规格：**
- 比较all_ku.json的mtime与hybrid_index.pkl的mtime
- 若json更新 > pkl更新，报警"索引过期"
- 可选：计算json的content hash，与pkl内存储的hash比对

**执行方式：** `python -m gotchas.tests.test_index_freshness`
**通过标准：** 索引mtime ≥ 数据mtime

## 二、设计师Schema验证闭环（心法①②落地）

> 当前状态：Schema尚未实现。以下为设计规格，待Phase1开发时落地。

### Schema定义（23字段，待确认）

设计师入驻/接单时需填写的结构化信息，等价于Boris的SPEC.md——"先定义清楚要什么，再让AI去匹配"。

### Schema自检规则

| 检查类型 | 规则示例 | 阻断级别 |
|---------|---------|---------|
| 必填完整性 | 城市、从业年限、擅长风格、服务类型 不可为空 | 阻断 |
| 逻辑一致性 | 从业年限 ≥ 5 时，案例数量不可为0 | 阻断 |
| 格式合规 | 手机号11位、微信号无特殊字符 | 阻断 |
| 质量评分 | 案例描述 < 50字 → 提示"描述过短，影响匹配精度" | 警告 |
| 交叉验证 | 城市=沈阳 时，服务区域应包含沈阳下辖区 | 警告 |

### 闭环反馈（心法③的延伸）

Schema不是填完就完了。Boris的核心洞察：**没有反馈的AI预测是"猜"。**

```
设计师填写Schema → AI生成业主匹配推荐 → 业主是否成交？
                                              ↓
                                    成交 → 强化该Schema字段权重
                                    未成交 → 分析哪个字段误导了匹配
                                              ↓
                                    修正匹配算法 / 提示设计师补充信息
```

**落地最小版本：** 每次谈单结果（成/未成）记录到usage_log，按月统计"哪些Schema字段与成交率强相关"。

## 四、与Boris心法的对应关系（总结）

**心法③"给AI自检工具"是知设当前最大短板。** Boris说"没有验证，AI是在猜；有验证，质量提升2-3倍"。

对应到知设：
- 我（AI）每次改完KU说"修好了"，但如果没有回归测试跑一遍，这就是在"猜"
- 你（小马哥）每次校准完说"这条对了"，但如果没有脚本确认下游532条引用都同步了，就可能漏

**自检工具的本质：把"人盯着确认"变成"机器自动拦截"。** 这就是Boris说的Hooks（生命周期钩子）——不是建议，是强制门禁。
